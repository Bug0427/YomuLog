# YomuLog — Supabase bootstrap pack (ordered, re-run-safe)

Owner-facing. This file is the **authoritative ordered sequence** for setting up a
Supabase project for YomuLog — brand-new project or an existing one. It replaces
the improvised order previously documented in `supabase/README.md` §2/§3 (those
sections now point here).

Two things are verified for every statement in this pack:

1. it runs on a real PostgreSQL engine, and
2. it can be **run twice in a row** on the same database without error (§6 has the
   full evidence).

---

## 0. TL;DR

1. Supabase Dashboard → **SQL Editor** → New query → paste
   **`supabase/bootstrap-one-paste.sql`** → **Run**. Done — that is all the DDL.
2. Deploy the Edge Functions and set their secrets (§4).
3. Rebuild the web app with the three env vars (§5).
4. Verify with the queries in §3.

There is **no separate "base DDL" step**: everything the migrations assume is
either already provided by Supabase or created by the pack itself (§1).

## 2. The ordered list (authoritative)

Run in this order. `supabase/bootstrap-one-paste.sql` is this list concatenated,
generated by `bash scripts/build-supabase-bootstrap.sh` — if you add a migration,
add it to that script **and** to this table.

| # | File | Creates / does | Re-run safety mechanism |
|---|---|---|---|
| 1 | `services/migrations/001_reading_progress.sql` | `reading_progress` + own-rows RLS | `CREATE TABLE IF NOT EXISTS`, `CREATE INDEX IF NOT EXISTS`, `DROP POLICY IF EXISTS` before each `CREATE POLICY` |
| 2 | `services/migrations/002_user_library.sql` | `user_library` | same |
| 3 | `services/migrations/003_download_queue.sql` | `download_queue` | same |
| 4 | `services/migrations/004_sync_state.sql` | `sync_state` | same |
| 5 | `services/migrations/005_user_preferences.sql` | `user_preferences` | same |
| 6 | `services/migrations/006_user_subscriptions.sql` | **Premium entitlement**: canonical `user_subscriptions` (`id` PK, `user_id` UNIQUE, `plan`/`is_active`/`current_period_end`), `stripe_event_created_at` high-water column, service-role-only writes, `upsert_subscription(...)` RPC | `ADD COLUMN IF NOT EXISTS`, `DROP POLICY/FUNCTION IF EXISTS`, `CREATE OR REPLACE`, repetition-safe `REVOKE`/`GRANT` |
| 7 | `services/migrations/007_stripe_edge_functions.sql` | **comments only** — reference doc for the Edge Functions (secrets they read, auth model). No SQL effect. | n/a |
| 8 | `services/migrations/008_collections.sql` | `user_collections`, `user_manga_tags` | as rows 1-5 |
| 9 | `services/migrations/009_user_activity.sql` | `user_activity` (KPI 1 retention heartbeat) | `CREATE TABLE IF NOT EXISTS` + `pg_policies` DO-block guard |
| 10 | `services/migrations/010_reading_stats.sql` | `reading_stats` + `reading_progress.seconds_read` (KPI 2) | `ADD COLUMN IF NOT EXISTS` + DO-block guard. **Requires 001** |
| 11 | `services/migrations/011_user_events.sql` | `user_events` (KPI 4 funnel) | `CREATE TABLE IF NOT EXISTS` + DO-block guard |
| 12 | `supabase/seed-test-users.sql` | the three auth test users + the **paid row flip** on `paid@yomulog.test` | per-email `DO` guard; `ON CONFLICT (user_id) DO UPDATE` re-applies the paid state |
| 13 | `supabase/realtime-publication.sql` | adds `user_subscriptions` to `supabase_realtime` (+ `replica identity full`) | `pg_publication_tables` guard; `alter publication` runs at most once |

### Ordering notes

- **6 before 12.** Migration 006 is canonical for `user_subscriptions`. The seed
  contains a defensive `create table if not exists` for the same table, so if the
  seed runs *first* that statement wins and you are left with the seed's looser
  shape (no `plan` CHECK, no `stripe_event_created_at` until 006 runs). Running
  006 first makes the seed's `create table` a harmless no-op. Either order works,
  but 6 before 12 is the one that is verified end to end.
- **10 after 1** — it `ALTER TABLE reading_progress ADD COLUMN IF NOT EXISTS`.
- **13 after 6** (the publication needs the table).
- If you already pasted the historical README DDL or the seed on this project:
  nothing breaks — just make sure 006 runs (see §7 "updating an existing project").

## 3. Verify (run once after the pack)

Paste into the SQL Editor; expected results are from the verified local run (§6).

```sql
-- 11 tables
select table_name from information_schema.tables
 where table_schema = 'public' order by table_name;
-- expect: download_queue, reading_progress, reading_stats, sync_state,
--         user_activity, user_collections, user_events, user_library,
--         user_manga_tags, user_preferences, user_subscriptions

-- entitlement writes are service-role only; clients may only read their own row
select has_table_privilege('anon',          'public.user_subscriptions','SELECT') as anon_select,     -- f
       has_table_privilege('authenticated', 'public.user_subscriptions','SELECT') as auth_select,     -- t
       has_table_privilege('authenticated', 'public.user_subscriptions','UPDATE') as auth_update,     -- f
       has_table_privilege('service_role',  'public.user_subscriptions','INSERT') as svc_insert;      -- t

-- the RPC is service-role only, and there is exactly one overload (8 args)
select p.proname, pg_get_function_identity_arguments(p.oid) as args,
       has_function_privilege('authenticated', p.oid, 'EXECUTE') as auth_exec   -- f
  from pg_proc p join pg_namespace n on n.oid = p.pronamespace
 where n.nspname = 'public' and p.proname = 'upsert_subscription';

-- seed
select count(*) from auth.users where email like '%yomulog.test';              -- 3
select u.email, s.is_active, s.plan from public.user_subscriptions s
  join auth.users u on u.id = s.user_id;                                       -- paid@yomulog.test | t | monthly

-- realtime
select tablename from pg_publication_tables
 where pubname = 'supabase_realtime' and tablename = 'user_subscriptions';     -- 1 row
```

## 4. Deploy the Edge Functions and set their secrets

The four functions are in `supabase/functions/`. None of them is a public
endpoint: `stripe-portal` / `stripe-cancel` verify the caller's Supabase access
token themselves, `stripe-webhook` verifies the Stripe signature, and
`mangadex-proxy` is the CORS proxy.

```bash
# once
supabase login
supabase link --project-ref <your-project-ref>

# one deploy per function — the JWT-verification flag is PER-FUNCTION, not global.
#  - mangadex-proxy  → MUST pass --no-verify-jwt: the browser calls it with a bare
#    fetch() and no Authorization header (services/mangaAPI.ts:101,129,164,209,239,333),
#    so platform JWT verification would 401 every proxied MangaDex request.
#  - stripe-webhook  → MUST pass --no-verify-jwt: its caller is Stripe, which sends a
#    Stripe-Signature header, never a Supabase JWT; requiring one 401s every entitlement write.
#  - stripe-portal / stripe-cancel → keep verification ON (no flag): the app sends the
#    caller's access token (services/stripeService.ts:260,296) and the functions hard-fail
#    without it (they check it via Supabase Auth /auth/v1/user themselves).
supabase functions deploy mangadex-proxy --no-verify-jwt
supabase functions deploy stripe-webhook --no-verify-jwt
supabase functions deploy stripe-portal
supabase functions deploy stripe-cancel
```

Secrets — exactly what the code reads via `Deno.env.get(...)`:

```bash
supabase secrets set \
  STRIPE_SECRET_KEY=sk_live_... \
  STRIPE_WEBHOOK_SECRET=whsec_... \
  SUPABASE_SERVICE_ROLE_KEY=... \
  SUPABASE_URL=https://<your-project-ref>.supabase.co
```

| Secret | Read by | Where the value comes from |
|---|---|---|
| `STRIPE_SECRET_KEY` | `stripe-portal/index.ts:69`, `stripe-cancel/index.ts:68`, `stripe-webhook/index.ts:76` | Stripe Dashboard → Developers → API keys → Secret key |
| `STRIPE_WEBHOOK_SECRET` | `stripe-webhook/index.ts:77` only | Stripe Dashboard → Developers → Webhooks → your endpoint → Signing secret |
| `SUPABASE_URL` | the three Stripe functions (`stripe-portal:70`, `stripe-cancel:69`, `stripe-webhook:78`) | Supabase → Settings → API → Project URL |
| `SUPABASE_SERVICE_ROLE_KEY` | the three Stripe functions (`stripe-portal:71`, `stripe-cancel:70`, `stripe-webhook:79`) | Supabase → Settings → API → Project API keys → `service_role` (reveal) |

Not needed: price IDs / plan IDs. Checkout is a **hosted Stripe link**, no
function reads a price ID (see `007_stripe_edge_functions.sql`).

Then register the webhook endpoint in Stripe:

- URL: `https://<your-project-ref>.supabase.co/functions/v1/stripe-webhook`
- Events: `checkout.session.completed`, `customer.subscription.created`,
  `customer.subscription.updated`, `customer.subscription.deleted`,
  `invoice.payment_failed`

`stripe-webhook` applies Stripe events in `event.created` order and ignores stale
ones, so retries and out-of-order delivery cannot flip entitlement state back.

## 6. Re-run-safety proof (how this was verified)

Method: a real PostgreSQL 16.15 engine, primed once with a local stub of the
pieces Supabase provides (`auth.users`, `auth.uid()`, the three roles,
`supabase_realtime`, Supabase's permissive default grants,
`supabase/tests/../../` — see `/home/team/shared/supabase-bootstrap/`), then:

- each of the 13 files run in order with `ON_ERROR_STOP=1` → **13/13 EXIT 0**;
- the **same 13 files run a second time on the same database** → **13/13 EXIT 0**;
- the consolidated `supabase/bootstrap-one-paste.sql` run twice on a fresh
  database → **EXIT 0, EXIT 0**.

Behavioural checks from the same run (not just "it parsed"):

- grants: `anon` = none, `authenticated` = `SELECT` only, `service_role` = write;
- `upsert_subscription` = one overload, `EXECUTE` for `service_role` only;
- RLS as the `authenticated` role: the paid user sees 1 row, the free user 0,
  and an `UPDATE` is rejected with `insufficient_privilege`;
- stale-event guard: event `2026-09-10` sets active; a late event `2026-09-09`
  that says "not active" is **ignored** (row stays active, high-water unchanged);
  event `2026-09-11` applies;
- `supabase_realtime` contains `user_subscriptions`; seed creates 3 users.

Artifacts: `/home/team/shared/supabase-bootstrap/` (stub, runners, `verify.sql`,
raw logs). Re-run with `bash run.sh <repo> <workdir>`.

Caveat, stated plainly: the engine was PostgreSQL 16, **not** a live Supabase
project, and the proof covers schema/RLS/RPC semantics — not the dashboard,
network or Auth service. The pieces Supabase itself provides are stubbed rather
than exercised.

## 7. Updating an existing project

- Everything in this pack is safe to re-run at any time.
- **Re-run migration 006** if the project was set up before PR #242: it adds
  `stripe_event_created_at`, the write-scoped policies, the client grant
  revocations and the 8-argument `upsert_subscription`, and drops the old
  7-argument overload. Nothing else changed.
- After the pack, `pg_policies` for `user_subscriptions` legitimately shows five
  policies: three `TO service_role` write policies, the `authenticated` SELECT
  policy, and (if the seed ran) the seed's own `user_subscriptions_select_own`
  SELECT policy. The extra SELECT policy is harmless — it is the same own-rows
  predicate and `anon` has no table grant at all.
